\section{Introduction}
\label{sec:intro}
Consider two maintainers editing an interface. One widens the range returned by a parser; the other adds a caller assuming the old range. Separate CI jobs can both pass against the same base revision, and a textual Git merge can succeed even though running the combined tree fails tests. A merge queue that batches both changes can detect the interaction early at the cost of delaying both, whereas a queue that separates them can produce two passing runs whose combined state remains untested. Which changes to group and what a passing test authorizes are therefore distinct engineering decisions.

Batch testing amortizes CI startup and execution costs across changes~\cite{beheshtian2022software,fallahzadeh2023accelerating,fallahzadeh2025contrasting}, while speculative execution hides integration latency by testing cumulative candidate states ahead of the branch frontier~\cite{zuul2026gating,ananthanarayanan2019keeping}. Both techniques shift work into recovery: bisection spends tests to isolate culprits, transient failures can trigger false rejections of clean singletons, and passing unstacked runs become stale whenever another worker advances the target branch. Queue operators readily observe changed file paths and workflow outcomes, not latent semantic interference between unmerged changes.

We study the Semantic Speculative Merge Queue (SSMQ), an unstacked exact-tree policy pairing head-anchored cone-disjoint packing with bounded Beta-Binomial retries and one-step traceback-guided splitting. Its structural predictor estimates affected files from warm-up co-change and directory membership, while commit authority comes strictly from verifying the exact prospective mainline tree rather than consulting any commit-time oracle.

We address four empirical questions. First, how often do public merge windows admit disjoint directory batches, and what do native GitHub Merge Queue logs actually reveal---and fail to reveal---about real admissions, evictions, durations, and causal attribution? Second, under identical unstacked exact-tree verification and decoupled priors, does filtering mega-PRs and directory cliques (\texttt{SSMQ-FilteredCone}) turn cone exclusion into a net improvement over \texttt{SSMQ-NoCone} across latency, clean false rejections (FRR), and runner cost? Third, how do grounded exact-tree adaptations of published batching and queue semantics (\texttt{BatchStop4}, historical \texttt{bors-ng}, GitHub Merge Queue \texttt{ALLGREEN}, PRediBatch-inspired risk grouping, and Aviator-inspired directory lanes) behave under shared capacity, and why does membership partitioning preclude causal cross-architecture ranking in this fault model? Fourth, in counterbalanced executable Git and QuixBugs experiments, when does function-level AST ranking actually reduce tests beyond a weight-matched file ranker, and when does accepting a stale pass break the branch?

Our central findings are bounded and largely negative for unstacked structural separation. Unfiltered co-change cones collapse batch width and inflate both stale-base invalidations and FRR. Filtering mega-PRs and directory cliques removes most of that blowup, yet \texttt{SSMQ-FilteredCone} still fails to deliver a consistent net win over \texttt{SSMQ-NoCone}: a modest nominal latency shift comes with higher FRR and an insignificant sign test, while saturated, directory-proxy, and uniform-null regimes are null or slower. Likewise, stopping bisection early (\texttt{Beheshtian-BatchStop4}) increases stale rechecks and FRR inside the same unstacked family, and file-disjoint packing eliminates the co-file sibling batches where AST function ranking outperforms file ranking.
